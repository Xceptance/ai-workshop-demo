# 04. Observability, Token Accounting & Disk Audit Logging

## 1. The Anatomy of an Agent Execution Trace

To debug or audit an AI agent, every turn must produce an immutable, replayable record.

In this project, every conversation session creates a dedicated directory under `./logs/sessions/{sessionId}/`:

```
logs/sessions/
└── 7a8f9b2c/
    ├── summary.json            # High-level metadata, total tokens, status, timing
    ├── trace_events.jsonl      # Streaming line-delimited events for each step
    ├── raw_payloads.json       # Exact message arrays and tool schemas sent to Gemini
    └── transcript.md           # Human-readable Markdown report with collapsible drawers
```

---

## 2. File Specifications

### 1. `summary.json`
Provides at-a-glance metrics for monitoring and cost accounting:
```json
{
  "sessionId": "7a8f9b2c",
  "title": "Workshop Session 7a8f9b",
  "modelName": "gemini-3.7-flash",
  "createdAt": "2026-08-18T12:50:00Z",
  "updatedAt": "2026-08-18T12:50:03Z",
  "messageCount": 2,
  "stepEventCount": 6,
  "tokenStats": {
    "inputTokens": 412,
    "outputTokens": 84,
    "totalTokens": 496,
    "durationMs": 1420,
    "estimatedCostUsd": 0.000056
  }
}
```

### 2. `trace_events.jsonl`
Every single micro-step (e.g. `USER_INPUT`, `CONTEXT_ASSEMBLY`, `TOOL_CALL_REQUEST`, `TOOL_EXECUTION`, `TOOL_OBSERVATION`, `FINAL_SYNTHESIS`) is written as a JSON object per line. This enables structured log ingestion into Elasticsearch, Splunk, or Datadog.

### 3. `transcript.md`
A complete GitHub Flavored Markdown document containing:
- Session metadata and total token consumption.
- Conversation dialogue between user and agent.
- Granular `<details><summary>` cards with the exact raw JSON arguments and outputs.

## 3. Understanding Token Consumption & Cost

Tokens are the fundamental billing unit of LLMs:
- **Prompt (Input) Tokens**: Billed whenever context, history, and tool definitions are transmitted to the API.
- **Completion (Output) Tokens**: Billed for tokens generated by the model (including tool call requests and thoughts).

### Context Window Growth Pattern:
Notice how prompt tokens increase on every turn:

$$\text{Prompt Tokens}_{\text{Turn } n} = \text{System Prompt} + \sum_{i=1}^{n-1}(\text{Messages}_i + \text{Tool Results}_i) + \text{Tool Schemas}$$

In multi-step agents, 90% of token consumption is typically **input tokens** from feeding back tool observations. Using lightweight, fast models like `gemini-3.7-flash` or `gemini-1.5-flash` keeps latency under 1 second and cost per query under a fraction of a cent.

## 4. Debugging Common Agent Failure Modes

| Failure Mode | Symptom | How to Inspect in Disk Logs | Solution |
|---|---|---|---|
| **Infinite Tool Loop** | Agent calls the same tool repeatedly without terminating. | Check `trace_events.jsonl` for repeating `TOOL_CALL_REQUEST` events. | Set `agent.max-steps: 10` and refine tool description to clarify when to stop. |
| **Argument Hallucination** | Model invents parameter names not defined in the schema. | Inspect `raw_payloads.json` vs. tool method parameters. | Add explicit `@P("...")` parameter annotations to guide the model. |
| **Tool Execution Exception** | Tool throws unhandled runtime exception (e.g. NPE, FileNotFound). | Check `TOOL_OBSERVATION` for `ERROR: ...` prefixes. | Return helpful diagnostic error strings from tool methods so the model can self-correct. |
